# 实验设计框架（教师向）

> 从"想让学生学到什么"到"怎么知道他学会了"的完整流程，用于**设计一个新实验**。
>
> **设计原则（2026-10-08 明确）：教学优先。** 这个平台的目的是**让学生理解知识**（读完题、读懂示范、
> 自己动手、看到反馈），判分只是"他做完了"的确认手段，不是设计目标。因此：
> **不要为了"区分学生"而制造陷阱**；把精力放在"讲清概念 + 给一份能对照的示范 + 给到位的反馈"上。
>
> 三份文档的分工：
>
> | 文档 | 回答什么 | 读者 |
> |---|---|---|
> | **本文** | 一个实验怎么设计（学习目标 / 任务 / 材料 / 导学 / 反思 / 判分 / 上线） | 出题教师 |
> | `docs/EXPERIMENT-PACKAGE-SPEC.md` | 上传的包**技术格式**（manifest 字段、cases 约定、依赖预装集） | 出题教师 |
> | `HANDOFF.md` | 平台运行态、镜像 tag、部署与回滚 | 平台维护者 |
>
> 可直接复制的骨架：`server/fixtures/ml-basics/`（**教学向样板**：题目包内含参考实现 + 4 个教学字段写实）、
> `server/fixtures/sales-report/`（表格类）、`server/fixtures/csv-cleaner/`（最简，内置回落型）。

## 0. 一个实验的五要素

```
① 实验目的  →  ② 任务与口径  →  ③ 材料（两个 ZIP）  →  ④ 学生过程  →  ⑤ 评判
   （能力点）      （可复现）        （模板 + 题目包）      （领取→自测→提交）   （机器 + 教师）
```

关键前提：**平台只判一件事 —— 学生交付的 Skill 能不能在标准用例上跑出正确结果**。
所以每个要素都要能被机器观测到 —— 这是本框架与普通实验指导书最大的区别。

> 平台曾在每个用例上额外跑一轮"只给题干"的 baseline，用来度量 `lift`（用 Skill 比裸做强多少）。
> **该对比已于 2026-10-06 取消**：实验面向学生的练习，不是严格考试，只看"最终结果对不对"。
> 因此本文里凡涉及 baseline / lift 的历史说明都已按单轮口径改写。

---

## 0.1 适用范围：这不是"机器学习专用"的框架

平台机制是**任务无关**的。复验对每个 case 只做四件事：

1. 把 `cases/<case>/` 里的输入文件拷进一个干净工作目录
2. 跑一轮 dsh —— 题干（`task.md`）+ 学生的 Skill
3. 把 `manifest.outputFile` 指向的产出与同目录的 `expected.*` 比对
4. 按 `judge.md` 的细则判定 `{pass, score, rationale}`

驱动里唯一的"任务特定"代码是**内置回落**（当包内没有 `task.md` / `judge.md` 时才用到的
"CSV 数据清洗"语义）—— 一旦你带上自己的 `task.md` + `judge.md`，就完全不涉及它。
所以"ML 味"只出现在本文的**举例**里（`class_weight`、accuracy 等），不是能力边界。

### 一条判断规则

> 若你的实验能写成「**给一份输入文件 + 一段自包含的指令 → 产出一个可自动比对的输出文件**」，
> 它就能上这个平台，与学科无关。

### 哪些实验已经能直接做（库里已有支撑）

| 任务族 | 典型形态 | 可用依赖（镜像已预装） |
|---|---|---|
| 数据清洗 / 转换 | 脏 CSV/JSON → 规整结果 | `csv` `json` `pandas` `openpyxl` |
| 文本与网页抽取 | 杂文本/HTML → 结构化 JSON | `re` `bs4` `lxml` `yaml` |
| 算法实现与评测 | 实现并跑出结果文件 | 标准库（`heapq` `graphlib` `decimal`…） |
| SQL / 数据库 | 建库查询 → 结果集 | **`sqlite3`（标准库）** |
| 统计与建模 | 数据 → 指标报告 | `scipy` `statsmodels` `sklearn` |
| 图像处理 | 图片 → 尺寸/统计/转换 | **`PIL`（随 matplotlib 装入）** |
| 代码修复 / 测试驱动 | 给带 bug 的实现 + 测试 → 修好的文件 | **`pytest`** |
| 文件格式 / 打包 | 归档、编码、diff | `zipfile` `base64` `difflib` |
| HTTP 客户端逻辑 | 解析本地响应样本（**不能真联网**） | `requests` |
| 深度学习（CPU） | 小模型训练/推理 → 指标 | `torch`（CPU 版） |

### 哪些做不到 / 要改造

| 限制 | 后果 | 怎么办 |
|---|---|---|
| 产出必须是**一个**可自动比对的**文本文件** | 多文件/目录型交付，判分只能看其中一个 | 在 `task.md` 里指定"主判据文件"作为 `outputFile`，其余作为过程产物 |
| 判分基于"与 `expected.*` 比对"（llm / exact） | **开放性/主观性产出**（设计方案、论文、评审意见）没有客观基准 | 这类只能靠教师人工评分（`rubric` + `teacherScore`），机器的"成功率"退化成 judge 的主观意见，参考价值有限 |
| 容器**无外网**（`--internal` + SNI 白名单，只放行模型 API） | 需要调外部服务、真爬取、下数据集的实验做不了 | 把外部数据/响应做成**本地 fixture** 放进 `cases/`（`requests` 可照常用于解析逻辑） |
| 运行时依赖必须预装 | 用到的库不在预装集 → 复验直接失败（`--check` 会提前报出来） | 换等价库，或让平台维护者加进镜像并重建（一学期一两次） |
| CPU / 内存 2g / 每轮 ≤300s / 容器整体 ≤ `timeoutSeconds` | 长时间训练、大模型微调、大数据集跑不完 | 缩小规模到 CPU 可完成；确需大规模则另做镜像与限额（属平台改造，不是包能解决的） |
| 有用例是**静态一对一**的 `input → expected` | 交互式/多轮对话型任务没有天然形态 | 把交互产物收敛成"给定对话记录 → 输出判定/结构化结果"这类单文件任务 |
| 白名单放行模型 API | 学生 Skill 理论上可自己调模型（消耗平台 key） | 一般不建议；若实验本身就是提示工程，需显式设计并接受该行为 |

## 1. ① 实验目的：写成"平台能测到的东西"

实验目的不能只写"掌握机器学习基本流程"，要落到平台真实产出的信号上。可用信号只有四个：

| 平台信号 | 来源 | 说明 |
|---|---|---|
| **复验成功率** | 逐 case 判定 | 用学生的 Skill 跑标准用例，通过比例（0~1）—— 判分主指标 |
| **证据一致性** | `.dshc` 证据包 + 逐文件 sha256 | 学生自报哈希 vs 平台容器内实测哈希 |
| **能力边界填写质量** | 扫 `SKILL.md` 的 `## 能力边界…` 小节（非空且无 `TODO`） | 布尔值 |
| **踩坑记录条数** | 扫 `SKILL.md` 的踩坑列表项 | 整数 |

**写法对照**

| 弱（测不到） | 强（落到信号） |
|---|---|
| 掌握逻辑回归的用法 | 在给定切分口径下复现指标（成功率 ≥ 2/3）；能说明模型不适用的情况（能力边界） |
| 熟悉数据清洗 | 3 个含脏数据的用例清洗后与期望输出一致；记录至少 2 条真实踩坑 |
| 了解 Skill 规范 | Skill 目录结构合规、可被平台装入并跑通用例（成功率 ≥ 2/3） |

> 每个实验建议只设 **2~3 个能力点**。能力点越多，题干越长、判分越糊。

## 2. ② 任务与口径：可复现是第一原则

### 2.1 口径必须钉死三件事

| 要素 | 必须写清 | 反例（口径含糊，学生只能猜） |
|---|---|---|
| **输入** | 文件名、列/字段含义、编码 | "给定一批销售数据" |
| **处理规则** | 每一步的判定与优先级 | "合理清洗一下" |
| **输出格式** | 文件名、结构、键名、精度 | "输出一个报告" |

参考 `server/fixtures/ml-basics/problem/task.md`：它把切分函数、`random_state`、指标名、四舍五入位数全写死，
所以同一份输入任何人跑都得到同一个期望值。

### 2.2 `task.md` 仍要自包含（理由变了：为了学生自测，不是为了 baseline）

复验只跑**一轮**：

```
treatment：题干 + 输入文件 + 学生的 Skill → 与同目录的 expected.* 比对
```

题干是这轮的唯一事实源，所以口径仍要写全 —— 但理由从"让 baseline 公平"变成了
**"学生本地自测与平台复验必须同口径"**：学生手里拿到的题目包（`problem.zip`）与复验用的是同一份材料，
题干少写一条口径，学生按自己的理解做"对了"，复验却判他错。
**把口径全部写进 `task.md`，不要藏进模板** —— 模板是学生写代码的起点，不是教师补口径的地方。

### 2.3 用例（cases）设计

每个 `cases/<case0N>/` 放 `input.*` + `expected.*`。建议 3 个档位：

| 档位 | 作用 | 例子 |
|---|---|---|
| **基础** | 常规路径，确认学生真的实现了 | 三地区三产品的正常汇总 |
| **边界** | 口径中的特例 | `units=0` 的行、并列的"冠军产品"（取码点序最小者） |
| **陷阱** | 最容易被想当然做错的地方 | 类别不平衡时需要 `class_weight="balanced"`；`stratify` 按口径该传/**不该传**；`model_params` 必须真透传 |

两条硬要求：

1. **指标不要是满分**。若期望值恰好 1.0 / 100%，那么"没做好"也会碰巧全对，实验失去区分度。
   实例：`ml-basics` 的五个 case 期望 `acc` 为 0.90 / 0.92 / **0.75**、`R²` 为 0.9861 / **0.4907**
   —— 其中 case05 用 `model_params: {"fit_intercept": false}` 专门做"照妖镜"：
   漏传 `model_params` 时 `R²` 会从 0.4907 跳到 ≈0.98，实现对不对一眼可见。
2. **`expected.*` 用参考实现算出来，并在与复验同一个镜像里算**。
   数值受库版本影响（sklearn 主版本变了，指标会变），`ml-basics` 的做法是：
   ```sh
   docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/w" --entrypoint python3 \
     nju-lab-verify:0.2.0-rc.2-pkg4 /w/skill-solution/scripts/train.py --regen-cases
   ```

### 2.4 难度与区分度（教学优先时，这一节可以放轻）

> **教学优先**：不必为了"区分学生"刻意加难。指标不是满分就够（真实感 + 便于解释），
> 学生之间的差距更多体现在**能不能讲清为什么**（能力边界/踩坑记录）与**有没有真的动手**（证据包）。

取消 baseline 对照后，难度只从**结果本身**看：

- **成功率接近 1**（用例几乎全过）说明题目偏易。这本身不算错，但如果你的教学重点是"让学生把方法
  沉淀成可复用资产"，应当通过**更细的口径**（更多 `model_params` 组合、多指标、边界样本）拉高难度，
  而不是把信息藏进模板。
- **成功率不高、学生之间差异明显**就是区分度的来源；`judge.md` 的 rationale 会指出错在哪，
  这是比分数更有用的教学反馈。
- 判分阈值不要写进 `judge.md` 之外的地方；`judge.md` 里明确"什么算通过"。

### 2.5 反作弊设计（注意：题目包会下发给学生，且**含参考实现**）

学生领取任务时会**下载题目包 `problem.zip`**（用于本地自测与对照学习）。2026-10-08 起
参考实现也随包下发（`problem/reference/`，见 §3.5）：

| 能放进包 | 不能放进包 |
|---|---|
| `task.md`（题干）、`judge.md`（判据）、`expected.*`、`README.md`、`manifest.json`、`reference/` | **造题工具（`tools/`）** |

`expected.*` 与参考实现公开都是刻意的（学生要自测、要对照），这与"以学会为目标"的教学一致；
**代价**是复验成功率不再区分"自己写的 / 抄来的" —— 原创性由**过程性材料**体现：
学生自己的 `SKILL.md`（能力边界 / 踩坑记录）与 `.dshc` 证据包。

骨架里仍不要放答案：`skill-template/scripts/*.py` 只留**结构 + `TODO` + 解释层**，
平台复验时会把骨架交给模型，它必须自己实现。

### 2.6 应用驱动的实验设计（2026-10-10 起推荐范式）

**要避免的形态**：把一个实验做成"多个算法变体"（换个模型、换个参数就是一个 case）——
学生的任务退化成"把 `params.json` 抄成代码"，学到的是 API 用法，不是"面对问题怎么选"。

**推荐范式：从一个应用需求出发，让学生走完四步**：

| 步 | 学生要回答的 | 落在材料哪里 |
|---|---|---|
| 1 **需求** | 要解决什么实际问题？给谁用？什么算成功？ | `task.md` 的业务背景 + 达标要求 |
| 2 **选模型** | 为什么用它？（回归还是分类？要可解释吗？样本量够吗？） | `task.md` 明确"模型由你决定"；骨架列出**要做哪些决策**（= 针对这个应用的技术选型） |
| 3 **实验** | 怎么切分、用哪些特征、怎么保证可复现？ | 骨架的 `TODO` + `reference/` 的示范 |
| 4 **测试** | 跟什么比（**基线**）？达标线是多少？结果怎么解释？ | `manifest.assertions`（硬性）+ `judge.md`（语义） |

**三条设计纪律**（照 `server/fixtures/aq-forecast/` 抄）：

1. **必须有基线**：没有基线，"模型好不好"无从谈起。达标线用**相对基线的比例**（尺度无关），
   例如"MAE ≤ 0.8 × 持久性基线"；基线要是现实里真实存在的朴素做法（如"沿用上一小时"）。
2. **达标线要能分开"不建模"和"真做"**：造数据时就把两端的成绩量出来，让"直接交基线"过不了、
   "用上特征/模型"能过，两边都留余量；判据用到的参考值写进 `expected.json` 供断言引用。
3. **判据分层**（见 §5.1）：算术/阈值的硬性条件写 `manifest.assertions`（代码判），
   语义性的（说清选择、自洽性、可疑地过于好）留给 `judge.md`（LLM 判）。
   **不要求数值等于参考实现** —— `expected.json` 存"参考水平 + 阈值参数"。
4. **每个实验都是完整的小项目**（2026-10-30 补充，2026-10-31 修正）：把四步落成**六步可走的流程**
   写进 `task.md` —— ① 看清需求 → ② **看一眼数据（并画图）** → ③ 定基线 → ④ **训练模型** →
   ⑤ **评估（并画图）** → ⑥ 写结论。

   **"小"不等于"省环节"，但也不要加环节**：实验可以只有一份小数据、一个简单模型，但这条链子要完整；
   反过来，**不要为了"显得严谨"而要求学生做多方案对比** —— 实测加这条之后，参考实现耗时从 40s
   涨到 124s，学生也要多做一轮，教学重点反而被稀释。把实验做成"某个技术点的练习"会断裂流程，
   堆一堆额外要求同样会。

   **用图说话**（机器学习实验最直观的表达）：② 与 ⑤ 都要求画图 ——

   - ② 看数据：目标分布（直方图）、特征与目标的关系（散点）、类别是否均衡（柱状图）；
   - ⑤ 评估结果：回归画"预测 vs 实际 + 残差"，分类画**混淆矩阵**，多分类再叠一张逐档指标；
   - 图存在工作目录的 `figures/` 下；**图上的标题与轴标签用英文** —— 镜像里没有中文字体，
     中文会渲染成方框（`matplotlib` 已预装，记得用 `Agg` 后端）。

   配套三条：

   - **题干**（`task.md`）列出六步，标明每步产出落在报告哪个字段；
   - **报告用 `figures` 字段承载图的结论**（judge 看不到图片本身，只能读文本）：
     `[{"path": "figures/xxx.png", "takeaway": "一句话"}]`；配一条**断言**核对
     "至少 2 张图，每张都有 `path` 与 ≥10 字的 `takeaway`"；
   - **`judge.md` 的语义项**判断 `takeaway` 是否"看图说话"（看数据图能说出分布 / 相关性 / 均衡度，
     评估图能说出拟合好坏或漏报误报）—— 这是语义判断，不写死数字。

**与"技术实验"的对照**：

| | 技术实验（旧，如改造前的 `ml-basics`） | 应用实验（新，`aq-forecast`） |
|---|---|---|
| 题干给什么 | 模型名 + 超参 + 切分口径 | 业务需求 + 达标要求 |
| 学生做什么 | 照口径写代码 | 选模型、定特征、建基线、解释结果 |
| case 是什么 | 同一动作的多个变体 | 同一应用的**不同数据**（换季节 / 换城市） |
| 判分 | 逐字段等于 `expected` | 断言（达标）+ 语义（说清选择） |
| 一个实验的容量 | 5 个算法变体 | **一个应用问题** |

> 拆成多个应用实验时，按"应用的**决策类型**"分，而不是按"算法种类"分：
> 回归估算（连续量 + 基线）、二分类筛查（不平衡 + 召回优先）、多分类分型（K 类 + macro 视角）……
> 每个实验让学生练**一类决策**。

> ⚠️ **别把上面这句读成"单个实验的定位"**（2026-11 实测教训）：它说的是**一学期里多个实验之间**
> 的切分维度。**单个实验内部不是"练一类决策"** —— 它是一个**完整的小应用**（见本节第 4 条的六步流程），
> 学生在这个应用里做**技术选型**（用什么模型/结构、要不要预处理、指标看哪个）并说清理由。
> 写实验定位时就写"这个应用要解决什么、数据长什么样、达标要求是什么"，**不要**写成"练 xxx 技术点" ——
> 后者会把六步链条断裂成"某个技术点的练习"，正是本节开头要避免的形态。

## 3. ③ 材料准备：一个题目包 + 两个 Skill

```
你的实验项目/
├── problem/           → problem.zip        题目包：题面 + 判据 + IO 契约 + 用例（标准，不可改）
│   ├── manifest.json  ← 输出文件名 / 输入 / judgeMode / 依赖声明
│   ├── task.md        ← 题干（自包含）
│   ├── judge.md       ← 评分细则
│   ├── README.md      ← 给学生看的说明（会下发）
│   └── cases/case0N/{input.*, expected.*}
├── skill-template/    → skill-template.zip 学生起点：SKILL.md 骨架 + TODO
├── skill-solution/                         满配 Skill = 标准答案（**不打包、不下发**）
└── tools/                                  造题工具等（可选，**不打包、不下发**）
```

> **同一形态、三种完成度**：`skill-template/` 与 `skill-solution/` 都是"Skill 根"
> （含 `SKILL.md`），差别只在 TODO 填没填、下发不下发。复验装入的是**学生提交的 Skill**，
> 不是模板 —— 模板只决定交付物的形态契约（唯一一层 `SKILL.md`）。
> 完整示例见 `server/fixtures/`（三块统一的三个示例项目）。

### 3.1 `SKILL.md` 的必备结构

平台会扫两个小节来产出上面第 1 节里的信号，**模板必须保留这两个标题**：

```markdown
---
name: <kebab-case 名，与目录一致>
description: <一句话说明"何时该用这个 Skill"，模型据此决定是否加载>
---

# <标题>

## 能力边界（TODO：学生补全）      ← 非空且不含 TODO 才算"填写了"
- 能处理：…
- TODO：本 Skill 不处理哪些情况？

## 使用方法
```sh
python3 scripts/xxx.py <输入> <输出>
```

## <处理/建模>口径（TODO：学生实现并在自测中验证）
1. TODO：…

## 自测
用平台下发的题目包（cases/）…

## 实测档案（TODO：学生填写，dossier）
- 自测时间：
- 用例通过率：/3
- 踩坑记录（pitfalls）：
  1.                                ← 列表项条数 = "踩坑记录条数"信号
```

> ⚠️ 扫描器看的是 `## 能力边界…` 这一节的正文**不含 `TODO` 字样**；模板里那句话本身带 `TODO`，
> 学生必须真的改写才会被计为"已填写"。

### 3.5 教学向设计清单（七件事 —— 照 `ml-basics` 抄）

| # | 做什么 | 落在哪 | 要点 |
|---|---|---|---|
| 1 | **学习目标** | 项目字段 `objectives` | 写"学完能讲清什么"（≤3 条），不要写"掌握 xx"这种验证不了的 |
| 2 | **知识铺垫** | 项目字段 `background` | 概念地图：本实验涉及的基本概念各是什么 —— 学生动手前的地图 |
| 3 | **导学步骤** | 项目字段 `description` | ≤8 步，**每步说明"在学什么"**；引用的环境要与现状一致（别写"虚拟机"） |
| 4 | **参考资料 / FAQ** | 项目字段 `references` / `faq` | 文档链接 + 常见误区；FAQ 优先写"我的指标为什么不对"这类 |
| 5 | **参考实现随包下发** | `problem/reference/` | 学生**先读后仿**；它同时是教师"题目可解性"自检的输入 |
| 6 | **骨架留解释层** | `skill-template/SKILL.md` | 不是只留 `TODO`，而是"**原理一句 + 最小示例 + 你要做的**"，并指向 `reference/` |
| 7 | **反思环节** | 骨架的「能力边界」「实测档案」 | 学生写下"能/不能做什么"与"踩过什么坑" —— **抄不来的部分**，也是知识内化的地方 |

> 前 4 项是**项目字段**（学生端会渲染 `objectives` / `background` / `description` / `references`，
> 见 `web/src/pages/student/ExperimentDetail.tsx`），后 3 项是**包内材料**。

**第 8 件：给工作区的 LLM 定角色 ——「引导监督模式」（2026-10-31 立，2026-11 按此定位修订）** ——
材料做得再好，如果陪学生的模型把六步一口气做完，学生仍然学不到东西。所以要在**学生端**注入
"引导监督模式"（落点：`dsh/nju-lab-client/src/host/guidance.ts` 的常驻 system prompt 段 + skill 手册）。

**定位要说清：这是学习过程，不是考察过程。** 目标是让学生**熟悉一个过程** —— 从"怎么分析一个应用场景"
到"怎么拿到结果、怎么交付出去"；**不要求学生自己拍板那些重要决定**。四条分寸：

- **引导**：带他按六步走（看清需求 → 看数据 → 定基线 → 建模 → 评估 → 写结论），每步先说清
  "这一步在干什么、为什么要有这一步"，再动手；
- **不必卡决定**：选什么模型、基线定多少这类决定，学生拿不准就**直接给建议、甚至替他定好**
  （先说清理由）—— 别把"必须他自己想出来"当门槛，也别把实验变成考试；
- **别把流程糊掉**：每一步都真的跑、结果真的看得见（他跑或模型跑都行，跑完讲给他听），
  不能一口气全做完、只回一句"已完成"；
- **监督是流程层面的**：跳步、漏了评估或结论、交付物不齐时**直接指出来并说明为什么要补** ——
  提醒，不是评分；
- 学生卡住（报错、概念不懂）时痛快地帮；`notes` / `figures.takeaway` / 实测档案**最好由学生写**，
  模型给结构、给例子、帮他改。

> 隔离要求：这类引导**只装在学生端**（工作台镜像 + 学生本地 kit），**复验容器不装** ——
> 否则复验的 agent 会跟着"只引导不代做"，实验直接跑不通（verify profile 里没有 `nju-lab-client`，天然隔离）。

**本阶段的边界（2026-10-31 决定，2026-11 复核后不变）**：暂不引入"无 AI 兜底"的检验环节，也**不把过程记录纳入自动判分**。
理由：改动大；本阶段的目的是让学生**掌握做一个实验的思路**（看懂需求 → 看数据 → 定基线 → 建模 →
评估 → 写结论），"知道该怎么思考"本身就是最大收获 —— 学生带着这个思路，后续可以自行迁移到具体应用。

> 已知的错位（留待将来处理）：定位是"熟悉流程"，而自动判分只看"产物是否达标"，过程记录只留档。
> 所以**引导指令是软约束**，学生理论上仍可外包且系统发现不了 —— 按"引导监督模式"的定位，
> 这本来就不是被考察的东西，不必当成缺陷去堵。
> 将来若要检查"是否真学会"，**首选迁移检验** —— 加一个"不给参考实现、不给骨架"的综合任务
> （只给需求与数据），材料结构与判据可直接复用现有实验。次选：从 session 日志 / `.dshc`
> 统计"首答行为"（先尝试再问 vs 直接要答案），供教师参考。
>
> **取舍要说清**：参考实现随包下发后，复验成功率不再能区分"自己写的"与"抄来的"。
> 教学优先下这是可接受的 —— 原创性由第 7 项（反思）与 `.dshc` 证据包体现。
> 若某次实验确实要看原创性，可以不放参考实现，但要在实验定位里写明原因。

## 4. ④ 学生过程（平台会怎么跑）

```
领取 claim ─→ 本地开发 ─→ 用 cases 自测 ─→ 提交 submit ─→ 平台复验 ─→ 学生看反馈
```

| 环节 | 平台行为 | 对实验设计的要求 |
|---|---|---|
| **领取** | 校验解锁规则（默认：完成该实验所属章节之前的全部已发布章节），下发模板 + 题目包 + 评估条件（模型/推理档位/工具白名单，此后钉死不可改） | 实验挂在正确的章节下，否则解锁条件错 |
| **开发** | 学生在工作区 `nju-lab/<assignmentId>/skill/` 里改模板 | 模板目录结构不能太深（Skill 根必须是含 `SKILL.md` 的那一层） |
| **自测** | 学生拿 `cases/` 自己比对 `expected.*` | 用例要能让学生自己判断对错 → `README.md` 里给自测命令 |
| **提交** | 自检 Skill 根 → 逐文件 sha256 → 打包 ZIP → 生成 `.dshc` 证据包 → 上传；**多版本**（上限 10） | 交付物是完整 Skill 目录，不是单个文件 |
| **复验** | 一次性容器：逐 case 跑一轮（题干 + 学生的 Skill）→ judge 逐 case 判定 | 容器整体超时 = `evalConfig.timeoutSeconds`（默认 600s）；**单轮 dsh 另有上限**（平台当前钉在 ≤300s）；用例太多太慢要设 `maxCases` |
| **反馈** | 学生端看复验结果 + 教师评语 | `judge.md` 的 rationale 会进反馈，写清"错在哪"对学生最有用 |

**给学生的两条经验规则**（可以写进课程说明）：

1. 第一次提交前至少用**全部** cases 自测一遍 —— 复验失败会浪费一次版本额度。
2. `SKILL.md` 的"能力边界"和"踩坑记录"是评分信号，不是走过场，如实写就行（别用模板里的 TODO 占位）。

## 5. ⑤ 评判：三层，最终以平台复验为准

### 5.1 第一层：机器复验（客观实测）

每个 case 跑一轮，产出 `{pass, score, rationale}`。汇总口径：

| 字段 | 含义 |
|---|---|
| `successRate` | 逐用例通过率（0~1）—— 判分的主指标 |
| `tokenCost` | 本轮 dsh 实测 token（+ judge 的开销） |
| 逐 case 明细 | 每 case 的 pass/score/rationale/exitCode/耗时/sessionId |
| `skillInfo` | `{boundariesDocumented, pitfallsRecorded}` |
| `integrityCheck` | `capsuleHashVerified`、`selfReportVsRerun`（`consistent` / `suspicious` / `no-self-report`） |
| `package` / `dependencyCheck` | 本次用的包声明与依赖自检快照（可追溯评测口径） |

判分模式二选一（由 `manifest.judgeMode` 声明，教师可在项目里覆盖）：

| 模式 | 判法 | 适用 |
|---|---|---|
| `llm`（默认） | 平台固定的判分外壳 + 你的 `judge.md` 细则，由模型判等 | 输出有格式弹性、需要"容忍无意义差异"的任务 |
| `exact` | 归一化换行/行尾空白后逐字节比对 | 输出高度确定、期望完全精确的任务 |

#### 判据要分层：**算术交给代码，语义交给模型**（2026-10-10 实测教训）

**应用驱动实验**（学生自选模型、判"是否达标"）**不能让 LLM 去算阈值**：
实测把"`MAE ≤ 0.8 × 基线`"写进 `judge.md`，同一个"不建模"的负样本被 LLM 判成了**通过**。
正确做法是分层：

| 层 | 谁判 | 写在哪 | 内容 |
|---|---|---|---|
| **硬性条件** | **驱动代码**（确定性） | `manifest.json` 的 `assertions` | 字段完整、数值范围、切分占比、**达标线**（比值/阈值）、基线是否可信 |
| **语义判断** | LLM judge | `judge.md` | `notes` 是否真说清、`model` 与指标是否自洽、是否可疑地过于好 |

`assertions` 是表达式数组，驱动逐条求值（结果必须严格为 `true`），任一条不成立 → 该 case 直接不通过，
**不会交给 LLM 判**；反过来，断言全过也仍需 LLM 认可语义项。可用变量：

```json
"assertions": [
  { "name": "达标：MAE 比持久性基线低 ≥20%",
    "expr": "out.metrics.mae <= expected.accept.mae_max_ratio_to_baseline * out.baseline.mae" },
  { "name": "切分覆盖全部样本", "expr": "out.n_train + out.n_test === expected.n_rows" }
]
```

- `out`：学生产出（`outputFile` 是 JSON 就自动解析成对象）、`expected`：该 case 的 `expected.*`
  （所以**参考值、阈值、样本数都可以放进 `expected.json`** 供断言引用）
- 另有 `abs` / `min` / `max` / `round`
- 题目包不写 `assertions` → 行为与历史版本完全一致（向后兼容）

> 副作用好处：判据里不再有算术项 → `judge.md` 变短、rationale 变短 → 不再撞 judge 的输出上限
> （历史坑：`max_tokens` 偏小会让长 rationale 被截断，`JSON.parse` 失败后整个 case 报
> `judge output not parseable`）。

`judge.md` 写法建议：

- **应用任务（达标判定）**：先声明"硬性条件由平台断言判定，你不必重算"，
  再列**语义**项（说清选择、自洽性、可疑地过于好、基线定义是否正确）；模板见
  `aq-forecast/problem/judge.md`
- **精确比对任务**：先写**键名/结构约束**（多键少键拼写不同都算不通过）→ 再写**数值容差**
  （例：绝对差 ≤ 0.001）→ 最后写**判定口径**（键序、缩进、空白不扣分）；模板见
  `ml-basics/problem/judge.md`
- 两种都要"指出具体哪一项、期望与实际各是多少" —— 这段会出现在学生反馈里

### 5.2 第二层：平台的建议分（固定公式，供参考）

```text
建议分 = min(100,
           成功率 × 55
         + (能力边界已填写 ? 20 : 10)
         + (证据一致 ? 10 : 5)
         + (tokenCost < 15000 ? 10 : 6))
```

- `成功率` = 逐用例通过率（0~1）。原 `lift` 项（15 分）在 2026-10-06 取消 baseline 后并入成功率
  （40 → 55）；`tokenCost` 也从"两轮之和"变成单轮，阈值按比例减半（30000 → 15000）。
- 上限 100；**注意**：这是平台的固定公式，**不读你自定义的 `rubric`**。`rubric` 是给你在批改页展示、
  以及手动打分时参考的维度清单（`[{name, weight}]`），权重之和不必等于 100。
- 如果这个实验不看 token 成本，可以在 rubric 里弱化它 —— 最终分由你自己给。

### 5.3 第三层：教师评分（最终成绩）

- 批改页：看复验明细 + judge rationale + 证据一致性 → 填 `教师评分` 与 `教师评语`，
  提交后提交状态变 `graded`。
- 成绩导出：`GET /api/projects/:id/grades.csv`（学号 / 姓名 / 任务状态 / 版本 / 提交时间 /
  提交状态 / 复验成功率 / Token 成本 / 建议分 / 教师评分 / 教师评语，Excel 友好）。
- 原则（平台设计）：**学生自报仅供参考，成绩以平台复验结果为准**；`.dshc` 证据包用于印证过程真实性。

### 5.4 评判口径设计的三个取舍

| 取舍 | 建议 |
|---|---|
| 用例数量 vs 成本 | 每个 case 一次 dsh 调用；先 `--max-cases 1` 试跑，确认口径后再放开全部 |
| 严格 vs 宽容 | 口径能写死的（键名、行数、取值集合）就写死用 `llm`；完全确定的输出才用 `exact` |
| 成功率 vs 过程分 | 成功率是客观的；"能力边界/踩坑"是过程分。两者权重在 rubric 里体现、由你手工落分 |

## 6. ⑥ 上线与验收

1. **打包 → `--check`**（§3.3，不烧 token）
2. **上传两个 ZIP** → 拿到 `fileId` → 项目详情里绑定（Skill 模板 / 题目包）
3. **确认项目挂对章节**（影响默认解锁规则）、填好截止时间、评分维度
4. **发布**：`draft → published` 时才为本课程学生生成任务（草稿不会派发）
5. **自测闭环**（强烈建议）：用一个测试学生账号走一遍
   `领取 → 开发 → 提交 → 复验 → 批改`，确认 judge rationale 是你能接受的措辞
6. **放开给全班**；期间用成绩导出跟进进度

### 常见故障对照

| 现象 | 多半原因 |
|---|---|
| 复验容器 `invalid skill package: no unique SKILL.md layer` | 模板 ZIP 里 `SKILL.md` 不唯一或层级不对 |
| 复验直接失败并报"依赖缺失" | `requires` 里的库不在镜像预装集 |
| 学生 claim 后**每个请求**都失败 | 项目 `evalConfig.reasoningEffort` 不是 `off/low/high/max`（教师端已限制为这四个值） |
| 学生领取时被拒 | 解锁规则：需完成该实验所属章节之前的全部**已发布**章节 |
| 复验超时 | 用例过多或单轮太慢 → 调 `evalConfig.timeoutSeconds`（容器整体）或 `maxCases` 收敛用例数 |
| 复验通过但分数低 | 看 `skillInfo`（边界/踩坑没写）与 `tokenCost`（超过 15000 会掉 4 分） |

- [ ] `expected.*` 在与复验同一个镜像里生成，并用独立方法复核过
- [ ] 包内**没有**参考实现或答案代码

**材料**
- [ ] `SKILL.md` 有 `## 能力边界…` 与踩坑记录小节，`scripts/` 只留骨架 + TODO
- [ ] `manifest.json` 的 `outputFile` / `inputs` 与 cases 实际文件一致
- [ ] `requires` 里每个库都在镜像预装集（`--check` 通过）
- [ ] `judge.md` 写清键名约束、数值容差、`pass/score` 口径

**上线**
- [ ] 项目挂对章节、截止时间已设、`rubric` 与能力点对应
- [ ] `--check` 退出码 0
- [ ] 发布前用测试学生跑通"领取→提交→复验→批改"

## 8. 常见坑（实测沉淀）

| 坑 | 说明 |
|---|---|
| 题干藏信息 | 复验只看"题干 + Skill"：题干没写的口径，学生只能猜，判分口径也跟着糊 |
| 期望值满分 | 实验失去区分度（`accuracy=1.0` 时"做错"也能对） |
| 在题目包里放答案 | 题目包会下发给学生（`skill-solution/` 与 `tools/` 不要打包） |
| 改了口径只改一处 | `task.md` / `judge.md` / 满配 Skill 三份事实源必须同步，然后重算 `expected` |
| 复验容器要联网 | 不可能：`--internal` 网络 + SNI 白名单，只有模型 API 可达 |
| 在教师页保存项目后 `judgeMode/maxCases` 丢失 | 已修（提交时会带回）；若发现旧数据缺失，重设一次即可 |
| 中途换题目包 | `expected.*` 是评分基准，改任一 case 即新版本；不要在有学生做的时候换 |
| 推理档位填官方 API 的值 | 平台只认 `off/low/high/max`（教师端下拉已限制），填 `medium/xhigh` 等会让学生端全挂 |

## 9. 附：把平台能力当作"可选信号"的对照表

| 你想考查的 | 用哪个机制 | 怎么设 |
|---|---|---|
| 结果正确性 | 复验成功率 | 用例 + `expected.*` + `judge.md` |
| 是否能说清边界 | 能力边界扫描 | 模板保留 `## 能力边界` 小节 |
| 是否真做过实验 | 踩坑记录 + `.dshc` 证据 | 模板保留"实测档案/踩坑记录"小节 |
| 过程是否真实 | 证据一致性 | 平台自动对照自报哈希与实测哈希（无需配置） |
| 效率意识 | tokenCost | 平台自动统计；在 rubric 里体现权重 |
| 工程规范 | 教师评分 | rubric 写维度，人工落分 |
