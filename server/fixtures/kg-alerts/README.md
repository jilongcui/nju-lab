## 场景与数据

- 应用：合理用药审查 —— 患者用着禁忌药、或同时用着互相作用的两种药，要**自动预警并给出推理路径**
- 对应章节：课程第 8 章《知识图谱》（正文里的禁忌证/相互作用两跳查询例子）
- 数据（虚构教学知识整理，**不是临床依据**）：

| 文件 | 内容 |
|---|---|
| `triples.csv` | 三元组 `head,relation,tail`：药物知识（禁忌证 / 相互作用 / 不良反应）+ 患者数据（患有 / 服用 / 过敏） |
| `ontology.json` | `entity_types`（实体名 → 类型）+ `relation_schema`（关系 → `{from,to}`） |
| `updates.json` | 图更新单：补录一位新患者 / 撤销一条医嘱 / 更正一条错误关系 / **一条违反本体的更新** |

| case | 规模 | 特点 |
|---|---|---|
| case01 | 8 位患者 / 36 节点 / 60 条边 | 常规 |
| case02 | 12 位患者 / 38 节点 / 78 条边 | 患者更多 |

**患者数据按种子生成，但**（`tools/gen_data.py`）：以较大概率**注入**两类冲突
（"疾病 ↔ 禁忌药"、"两味互相作用的药"），并在生成后**自检**"初始图里确实有禁忌证预警与
相互作用预警"，否则直接报错 —— 避免造出一份一条预警都出不来、没有信号的题。

## 判据设计要点

1. **口径钉死**：在用药 = `服用` / `医嘱使用`；禁忌证 = 患者疾病与药物禁忌疾病**在同一疾病上碰头**；
   相互作用 = 患者在用的两味药之间有边（**双向都算**）；**路径的三元组顺序**也写死 ——
   所以预警清单（含路径）是确定的，可以逐条比对。
2. **本体校验必须真的生效**：更新单里**故意放了一条违反本体的更新**（往"药物→疾病"的 `禁忌证`
   关系上塞了一个患者节点），断言要求 `crud.rejected_updates === 1` ——
   只检查"关系名存在"的写法能过关系名检查但过不了端点类型检查。
3. **更新要看得见**：断言同时核对**更新前**（`alerts_before`）与**更新后**（`alerts_after`）的两类预警。
   撤销医嘱应当让禁忌证预警减少、补录带冲突用药的患者应当带出新的相互作用预警 —— 各少/多一条都算错。
4. **路径是硬性要求**：每条预警都要带 ≥3 个三元组（`[患者,"患有",c]` / `[药,"禁忌证",c]` / `[患者,"服用",药]`），
   这就是"可解释"落到材料上的样子。
5. **语义交给 judge**：为什么用图（多跳 + 可追溯）、本体扮演什么角色、被拒绝的那条错在哪、
   更新后的变化、局限（没有 `过敏` 规则、没有剂量/时间窗、不给临床结论）。

### 出题时的实测依据（2026-10-10 在本机复验镜像里跑）

| case | 禁忌证预警 | 相互作用预警 | 被本体拒绝 |
|---|---|---|---|
| case01 | 5 → 4（撤销一条医嘱后消失） | 5 → 6（补录的患者带出一条） | 1 条 |
| case02 | 13 → 12 | 9 → 9（补录 +1、更正 −1） | 1 条 |

参考实现复验：**2/2 case 通过、硬性断言 11/11**（case02 的 judge 分 0.95），单轮 dsh 63s / 93s。

## 项目字段文案（上传到平台时用）

**objectives**

1. 能说清知识图谱为什么擅长"关系推理"：多跳沿边走、每条结论都能给出推理路径。
2. 能把一个医学问题落成"三元组建图 + 多跳查询"（患者—疾病—药物在同一个疾病上碰头）。
3. 能说清本体（实体类型 + 关系端点类型）的作用：它就是图上的 Schema，更新要按它校验。

**background**

- 知识图谱用**三元组** `(头实体, 关系, 尾实体)` 表示知识：`(二甲双胍, 禁忌证, 严重肾功能不全)`。
- 图的强项是**关系与推理**：多跳查询只是"沿边多走几步"，不像 SQL 那样每加一跳就要重写 JOIN。
- **可解释性**是它在医疗场景的杀手锏：结论能附上一条完整路径，医生看得出"为什么"。
- **本体**定义有哪些实体类型、每种关系连接哪两类实体；它约束"什么数据能进图"，
  相当于关系数据库里的 Schema（本实验的图更新就靠它拒绝非法数据）。
- 真实系统用 Cypher（Neo4j）/ SPARQL 做图查询；本实验用 Python 遍历（`networkx`），
  机制一样：邻接结构 + 走边。

**description**（导学步骤）

1. 读 `task.md`：看清建图口径、两类预警的判定与**路径顺序**、更新与本体校验口径。
2. **回头看本体**：`ontology.json` 的 `entity_types` 与 `relation_schema` 各是什么？
   更新为什么要按它校验？
3. **建图**：三元组 → 有向图，统计实体类型与关系类型。
4. **多跳预警**：把"患者—疾病—药物"在同一个疾病上碰头；在"患者在用的两味药"之间找相互作用边。
   **每条预警都要带完整路径**。
5. **图更新**：补录 / 撤销 / 更正，每条先过本体校验；那条违反本体的更新要**拒绝**并计数。
6. **更新后重跑预警**：撤销的医嘱应当让对应预警消失，补录的患者会带来新预警。
7. **画一张图**：更新前后两类预警数量对比（标题与轴标签用英文）。
8. **自测两个 case** 并与 `expected.json` 对照；把可解释性、本体的作用与局限写进 `SKILL.md` 的「实测档案」。

**references**

- 知识图谱概念（维基）：<https://en.wikipedia.org/wiki/Knowledge_graph>
- Cypher 查询语言（Neo4j）：<https://neo4j.com/docs/cypher-manual/current/>
- `networkx` 文档：<https://networkx.org/documentation/stable/>
- 课程第 8 章《知识图谱》；第 6/7 章（关系库与向量库）—— 四种知识形态的对照

**faq**

- **预警条数比 expected 多？** "在用药"要同时认 `服用` 与 `医嘱使用`；相互作用是**双向**的，两个方向都要查。
- **`rejected_updates` 是 0？** 本体校验要比对**端点类型**：`entity_types[head] == schema.from`
  且 `entity_types[tail] == schema.to`；只检查"关系名存在"会把非法更新放进来。
- **路径与 expected 不一致？** 按 `task.md` 表里的顺序抄（禁忌证 = 患者→疾病 / 药物→疾病 / 患者→药物）；
  相互作用要按**图里实际存在的方向**写。
- **更新后预警没变？** 更新完必须**重新跑**一遍预警查询，别拿更新前的对象算。
- **图里中文变方框？** 用英文标题/轴标签，中文写在 `takeaway` / `notes`。
