## 场景与数据

- 应用：把虚拟病例/指南条目做成"按意思找"的检索（章节第 7 章的「相似病例检索」场景）
- 对应章节：课程第 7 章《向量数据库》（正文里的余弦相似度玩具例子与检索演示）
- **离线可复现的向量化**：`concepts.json` 给一份**概念词表**（每个概念 = 一维 + 若干同义词），
  学生的 `embed(text)` = "按词表数同义词出现次数 → L2 归一化" → 余弦相似度 = 点积。
  于是「心梗」与「心肌梗死」落进同一维，**语义检索真的能工作**，且不需要联网、不需要下载模型。
- 对照实验：同一批查询再用**关键词检索**（字符 2-gram 计数）跑一遍，算两者各自的 `recall@3`。

| case | 规模 | 特点 |
|---|---|---|
| case01 | 40 条语料 / 12 维 / 8 条查询（4 条改写、2 条无关） | 常规 |
| case02 | 60 条语料 / 14 维 / 12 条查询 | 更大，多两个概念 |

**造题时的两条硬约束**（否则对照实验没意义，见 `tools/gen_data.py` 头部注释）：

1. 每个概念有一个**"查询专用"说法**，语料里**从不出现** → 改写查询字面上与相关文档不重叠；
2. 生成后**校验**该说法与全部相关文档没有任何 2-gram 重叠 → 关键词检索在改写查询上必然漏。
   （手工挑同义词很容易踩坑：「高血压病」与「高血压」共享 bigram，就漏不了了。）

## 判据设计要点

1. **口径钉死**：向量化（子串计数 / L2 归一化）、相似度（点积）、Top-K=3、**只返回分数 > 0**、
   同分按 `doc_id` 升序、关键词用字符 2-gram —— 全部写进 `task.md`，所以 Top-3 名单与 recall 确定。
2. **对照要成立**：断言里有一条 `recall_at_3_vector > recall_at_3_keyword` —— 这是本实验要让学生
   **亲眼看到**的现象，也是他 `notes` 里必须解释的东西。
3. **增删改查真的落到索引上**：断言核对 `crud` 各项条数、**更新后**的检索结果（`post_retrieval`）、
   以及**带科室过滤**的检索结果 —— 只"改文本不重算向量"会在这里露馅。
4. **语义交给 judge**：机制是否讲清（同义词→同一维→余弦大）、为什么关键词会漏、
   "改写要重算向量"这个坑、方案的局限（词表是人写的、真实场景要用训练好的 embedding）。
5. **图的 takeaway 与 metrics 自洽**（judge 判）；精确数值一律由断言负责。

### 出题时的实测依据（2026-10-10 在本机复验镜像里跑）

| case | 向量 recall@3 | 关键词 recall@3 | 差距 |
|---|---|---|---|
| case01 | **0.6464** | 0.1278 | 5.1× |
| case02 | **0.4345** | 0.1921 | 2.3× |

> 向量这边也不是满分很正常：相关文档常多于 3 篇（某概念可能有 10 篇语料），`recall@3` 的上限本来
> 就低于 1 —— 这正好让学生体会"召回要连同 K 一起看"。（case01 的 4 条改写查询里，关键词检索基本
> 全靠 `same_words` 类查询拿分。）

参考实现复验：**2/2 case 通过、硬性断言 12/12**，单轮 dsh 52s / 38s。

## 项目字段文案（上传到平台时用）

**objectives**

1. 能说清"向量化"在干什么：把一个"意思"编码成一串数字，语义相近则向量相近。
2. 能用余弦相似度做 Top-K 检索，并说清它和关键词检索的本质差别（同义扩展 vs 字面匹配）。
3. 能说清向量库的日常维护里最容易错的一步：**改写文本后必须重算向量**，否则检索按旧文本给分。

**background**

- Embedding：把文本/图像变成定长向量；训练好的模型保证"语义相近 → 向量距离近"。
- 本实验用**词表 + 计数**做同一件事的玩具版：每个概念占一维，它的同义词都算这一维 ——
  机制透明、离线可复现，真实模型是"学出来的"，机制一样。
- 余弦相似度：两个向量夹角的余弦；向量先做 **L2 归一化**之后，余弦就等于点积。
- 向量库 = 存储（id + 向量 + 元数据）+ 相似度检索（Top-K）；真实系统还会加 ANN 索引（HNSW/IVF）
  把"全量算一遍"加速到毫秒级 —— 本实验是全量算，规模小所以够用。
- 它回答"像不像"，不回答"准不准"；不能做统计、没有事务 —— 这正是它和关系数据库互补的地方。

**description**（导学步骤）

1. 读 `task.md`：看清向量化口径、两种检索口径、recall 的定义与 `output.json` 的键名。
2. **回头看概念**：为什么「心梗」和「心肌梗死」要落进同一维？L2 归一化解决什么问题？
3. **建立向量库**：把每条语料变成一个向量存起来（list / numpy / 文件都行）。
4. **检索 + 对照**：对每条查询取 Top-3；再用关键词检索跑同一批查询。
5. **增删改查**：新增一条、**改写一条（重算向量）**、删除一条，再做一次**带科室过滤**的检索。
6. **评估**：算两种检索的 `recall@3`，并想清楚为什么差这么多。
7. **画一张对比图**（标题与轴标签用英文），把结论写进 `figures[].takeaway`。
8. **自测两个 case** 并与 `expected.json` 对照；把机制、坑与局限写进 `SKILL.md` 的「实测档案」。

**references**

- 余弦相似度（维基）：<https://en.wikipedia.org/wiki/Cosine_similarity>
- HNSW / ANN 检索入门：<https://github.com/nmslib/hnswlib>
- 课程第 7 章《向量数据库》；上一章《知识库概念和文本内容》里的检索失败案例
- 参考实现：`problem/reference/scripts/search.py`

**faq**

- **改写查询的 Top-3 和 expected 不一致？** 向量化口径：子串计数（**不是分词**）、累加该概念
  **全部同义词**、逐维计数后 **L2 归一化**；相似度是**点积**。
- **关键词检索也命中了改写查询？** 2-gram 要**去重**；文档得分是这些 gram 在文档里出现的**总次数**。
- **每条查询都返回 3 条？** 口径是**只返回分数 > 0** 的结果 —— `unrelated` 查询应当返回空列表。
- **改写语料后检索结果没变？** `update_docs` 之后必须**重算**那一条的向量。
- **图里中文变方框？** 用英文标题/轴标签，中文写在 `takeaway` / `notes`。
