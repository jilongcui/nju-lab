# 相似病例检索 Skill（参考实现 · 学习示范）

> 📖 这份实现**随题目包一起下发**（`problem/reference/`），是给你的**示范** —— 不是标准答案。
> 判据只看"向量化/检索口径一致 + 更新后索引真的变了 + 说清机制与局限"，所以
> 向量存哪儿（list / numpy / SQLite blob）、索引怎么组织、代码怎么分层都随你。

## 能力边界

- 能处理：`corpus.csv` / `queries.csv` / `concepts.json` / `updates.json` 这套固定结构的输入
- 能处理：按词表做子串计数的"玩具版 embedding"（离线、确定、无外部依赖）
- 能处理：余弦 Top-K、只返回分数 > 0 的结果、同分按 `doc_id` 升序；带元数据（科室）过滤的检索
- 能处理：增删改（改写时**重算向量**）与"更新后的检索结果"对比
- 不处理：**训练出来的** embedding（没收录的同义词一概搜不到 —— 这是词表方案的硬边界）
- 不处理：中文分词/词形还原、ANN 索引（HNSW/IVF）与大规模性能（这里就是全量算余弦）
- 不处理：列名或文件结构与题干不同的输入

## 方法（六步 —— 与 `task.md` 的流程一致）

1. **看清需求** —— 要解决"字面不同、意思相近"，关键词检索为什么不够
2. **回头看概念** —— `embed`：概念维 + 同义词计数的本质是"把人写的语义关系编码进向量"
3. **建立向量库** —— `build_index`：doc_id → 向量（真实系统还会建 ANN 索引加速）
4. **检索 + 对照** —— `search`（余弦 Top-K）vs `keyword_topk`（字符 2-gram）
5. **增删改查** —— `apply_updates`：新增 / 改写（重算向量）/ 删除 / 带科室过滤的检索
6. **评估 + 结论** —— `recall_at_k` + 对比图 + `notes`（机制、坑、局限）

产出结构（`output.json`）见 `task.md`；判据见 `judge.md`。

## 实测档案

- 自测时间：
- 用例通过率：/2
- 关键数字：
  - case01（40 条语料 / 12 维 / 6 条计入评估的查询）：向量 recall@3 **0.6464**，关键词 **0.1278**
  - case02（60 条语料 / 14 维 / 9 条计入评估的查询）：向量 recall@3 **0.4345**，关键词 **0.1921**
  - 为什么向量这边也不是满分：相关文档常多于 3 篇（例如某概念有 10 篇语料），Top-3 最多命中 3 篇 →
    recall@3 上限本来就低于 1（这恰恰说明"召回"这个指标要连同 K 一起看）
- 踩坑记录（pitfalls）：
  - 改写查询必须与语料**字面无重叠**，否则关键词检索也能蹭到分 —— 这也是造题时要校验的东西
  - 口径是"只返回分数 > 0"：不这样规定，零分文档会按 `doc_id` 顺序挤进 Top-3，看起来"命中"了
  - 改写语料后**必须重算向量**：忘了重算，检索仍按旧文本给分，更新单等于白做
