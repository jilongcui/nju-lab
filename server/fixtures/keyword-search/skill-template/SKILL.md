# 关键词检索 Skill（你的方案）

> **本实验是应用任务，不是"按口径写代码"**：给你一个真实需求（科室要给文献库做检索入口），
> **代码怎么组织、图怎么画由你自己决定**。四套口径（索引 / 检索 / 基线 / 评估）是业务规则
> （必须照做），但"怎么实现"是你的自由 —— 达标看的是"口径一致 + 名单一致 + 指标对 + 说得清边界"。

## 实验材料（都在题目包 `problem/` 里，领取后工作区就有）

| 材料 | 作用 |
|---|---|
| `task.md` | **题干**：业务背景、六步流程、四套口径、交付格式 |
| `judge.md` | 判据：哪些是硬性口径、哪些是语义判断 |
| `reference/` | 一份**示范实现** —— 先读它，再写你自己的（它不是标准答案；函数划分与你的骨架一致） |
| `cases/case01`、`cases/case02` | 两种语料规模，自测用（每个 case 有 `expected.json` 可以对照） |

**实验流程（六步，与 `task.md` 一致 —— 每一步都要走完）**：

| 步 | 做什么 | 落在哪 |
|---|---|---|
| ① 看清需求 | 什么算"命中"、这类方法的天花板在哪 | 心里有数（写进 `notes`） |
| ② **看懂口径** | 切词 / 停用词表 / BM25 参数 / 并列规则 / 基线口径 —— **都不许改** | 心里有数 |
| ③ **建索引** | 词项 → 文档 的倒排索引，算词表大小与校验和 | 报告的 `index` |
| ④ **检索** | BM25 打分 → Top-3（降序，并列按 doc_id 升序） | 报告的 `retrieval` |
| ⑤ **对照与评估** | 同一个查询集跑字符 2-gram 基线，算 `recall@3`（含按类型分组），画图 | `baseline` / `metrics` / `figures` |
| ⑥ **写结论** | 讲清 BM25 的机制、改写查询为什么漏、还有什么局限 | 报告的 `notes` |

材料配合：`task.md`（需求 + 四套口径）→ 读 `reference/`（一份**走完这六步**的示范）→
回 `scripts/bm25_search.py` 填掉你自己的 TODO → 两个 case 都跑 → 补全能力边界（平台不检查）→ 提交；实测记录写进 `report.md`（平台按它评过程分）。

## 要做的决策（本实验的重点）

1. **为什么 BM25 要"长度归一化"**：如果去掉 `b`（等于让长文档占便宜），`recall@3` 会怎么变？
   对照的字符 2-gram 基线就是"完全没有归一化"的极端例子 —— 它的表现说明了什么？
2. **`k1`（词频饱和）解决什么问题**：一个词在文档里出现 20 次，真的比出现 2 次相关 10 倍吗？
   如果不做饱和会怎样？
3. **同一批指标为什么还能"分组"看**：只看总体 `recall@3` 会不会掩盖问题？
   分 `same_word` / `paraphrase` 之后，你看到了什么结论？
4. **这道坎要怎么过**：既然倒排索引搜不到"意思"，下一步该怎么办？（提示：第 7 章的向量检索
   是"按意思找"，但它也有自己的代价 —— 想得出来是什么吗？）

## 自测

两个 case 都要跑，并自己与 `cases/<case>/expected.json` 对照（口径对不对，一眼就能看出来）：

```sh
for c in cases/*/; do
  python3 scripts/bm25_search.py "$c" "/tmp/$(basename "$c").json"
done
```

> 卡住了怎么办：先看 `reference/scripts/bm25_search.py` 里对应的那一段，再回来改自己的实现。

> 实测记录（运行方式、结果、错误分布）写进同级的 `report.md`；这里只保留能力边界与已知失效情形。
