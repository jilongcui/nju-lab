评分细则（**把 harness 做成一个可分享的智能体应用**）

⚠️ 本章是**迁移检验 + 交付型**任务：学生拿到需求、数据与交付契约，**没有参考实现**。
可机器判定的部分（附件字数与校验和、`trace` 逐步、工具错误码、报告四节与指标表、计数、
记忆三态与行集变化、检索 top3、越界升级与拒答、`app.web_sha256` 与模板基线）已在 `task.md` 里钉死，
由平台用**确定性断言**判定（见 `manifest.json` 的 `assertions`）。断言未通过的结果**不会交给你判**，
你不必重算这些值。

你只需要判断以下**语义**问题（任一项不成立 → 不通过）：

1. **`notes` 是否说清"为什么自己解附件"**：要能说出 PDF / DOCX 分别是怎么存的（内容流里的文本操作符、
   OOXML 的 zip + XML），以及"先解析成结构化行"与"把 PDF 文本丢给模型"的差别（后者无法逐字段复核、
   也无法判断哪一行超参考区间）。只写"我实现了附件解析" → 不通过。
2. **有没有把"报告"写成"结论"**：报告可以汇总数值、给出处、提示复核；如果 `notes` 或报告正文出现
   "所以这个病人是感染 / 糖尿病控制不好"这类**诊断式断言**，即使字段都对 → 不通过。
3. **记忆是否被理解成"真的改变输出"**：要能说清"报告只列异常指标"为什么会影响行集、
   "忘掉 MEM01"之后为什么行集又变回来；把记忆说成"只是存了一个字段" → 不通过。
4. **有没有正视局限**：至少给出**两条**真实局限，例如：本实验的 PDF 是约定形态
   （未压缩文本流 + ASCII），真实 PDF 有压缩流与 CJK 字体；图片只登记尺寸、不做识别；
   前端是零依赖模板改的，没有构建链与复杂状态管理；检索只做字面 2-gram；
   应用运行在平台容器里、资源与并发都有限。
   只复述题干、只堆字段名、把 `notes` 写成运行日志 → 不通过。

判定口径：
- 键序、缩进、空白、措辞差异不扣分。数值与名单**由断言负责**，你不必复核；
  你只管「理由是否说清」与「有没有越界」。
- `score` = 上述语义项的达成程度（0~1）；任一项不成立时 score 不超过 0.5。
- rationale 用中文、**一句话（≤60 字）**说清结论；不通过时指出具体是哪一项。
