评分细则（**应用任务：建库 + 增删改查 + SQL 统计**）

⚠️ 清洗口径与查询口径已在 `task.md` 里钉死，所以行数、丢弃计数、查询结果是**确定的**。
这些数值与"更正是否落到库里""外键是否真的生效"已由平台用**确定性断言**判定（见 `manifest.json` 的
`assertions`）：字段完整、原始行数、入库行数、丢弃计数、表结构（主键/外键）、被拒绝的孤立报告、
增删改条数、三个查询结果、图与 `notes` 的基本要求。
断言未通过的结果**不会交给你判**，你不必重算这些数字。

你只需要判断以下**语义**问题（任一项不成立 → 不通过）：

1. **表结构是不是真的"关系式"设计**：应当按实体拆表（患者 / 就诊 / 检验），主键选在能唯一标识一行的列上，
   外键指向被引用表；`schema` 里报出来的结构要与 `notes` 里的说明一致。以下情况**不通过**：
   把三类信息挤进一张大宽表、用一列 JSON 文本塞下整行、外键指向一个并不唯一的列、
   `schema` 说是三张表而 `query_results` 的数字明显来自另一种结构（前后矛盾）。
2. **`profile.problems_found` 与 `dropped` 是否自洽**：说"数据没问题"却报出了被丢弃的行、
   或列出的问题类型与丢弃计数完全对不上（例如报了 19 行 invalid 却只提"日期格式"）→ 不通过。
   只写"数据比较脏"这类空话、不指出具体是哪几类问题 → 不通过。
3. **`figures[].takeaway` 是否"看图说话"且与 `query_results` 自洽**：结论里的数字（哪个科室最多、
   多少人）必须与报告的查询结果一致；只写"我画了一张柱状图"、或结论与数字矛盾 → 不通过。
4. **`notes` 是否讲清了机制与不足**：要说清"为什么要有主键/外键"以及"那条被拒绝的报告说明了什么"，
   并给出至少一条真实的不足（例如没做单位检查、没有记录谁改的）。
   复述题干、只堆字段名、或把 `notes` 写成操作流水（"我先建表再插入"）→ 不通过。

判定口径：
- 键序、缩进、空白、小数位、科室顺序差异不扣分。数值是否符合口径**由断言负责**，你不必复核；
  你只管「报告内部是否自洽」（例如 `takeaway` 里的人数与 `query_results` 对不上 → 不通过）。
- `score` = 上述语义项的达成程度（0~1）；任一项不成立时 score 不超过 0.5。
- rationale 用中文、**一句话（≤60 字）**说清结论；不通过时指出具体是哪一项。
