# 检验数据入库与查询 Skill（你的方案）

> **本实验是应用任务，不是"按口径写代码"**：给你一个真实需求（科室要一个能查、能改、能追溯的库），
> **表怎么设计、代码怎么组织由你自己决定**。清洗口径与查询口径是业务规则（必须照做），
> 但"怎么实现"是你的自由 —— 达标看的是"口径一致 + 更正真的落到库里 + 查询结果对不对 + 说清设计"。

## 实验材料（都在题目包 `problem/` 里，领取后工作区就有）

| 材料 | 作用 |
|---|---|
| `task.md` | **题干**：业务背景、六步流程、清洗/更正/查询口径、交付格式 |
| `judge.md` | 判据：哪些是硬性口径、哪些是语义判断 |
| `reference/` | 一份**示范实现** —— 先读它，再写你自己的（它不是标准答案；函数划分与你的骨架一致） |
| `cases/case01`、`cases/case02` | 两批数据，自测用（每个 case 有 `expected.json` 可以对照） |

**实验流程（六步，与 `task.md` 一致 —— 每一步都要走完）**：

| 步 | 做什么 | 落在哪 |
|---|---|---|
| ① 看清需求 | 为什么要主键 / 外键：唯一指认一行 vs 不留"查不到患者"的报告 | 心里有数 |
| ② **先摸清数据** | 数行数、数脏在哪几类（重复 / 空字段 / 非正数 / 日期格式 / 对不上的外键） | 报告的 `profile` |
| ③ **设计并建库** | 三张表怎么划分、主键选谁、外键指向谁、约束要不要开 | 报告的 `schema` |
| ④ **清洗入库** | 按口径清洗（顺序不能反）→ 入库，丢弃的计数 | 报告的 `loaded` / `dropped` |
| ⑤ **增删改查** | DELETE / UPDATE / INSERT，并观察外键拒绝了什么 | 报告的 `crud` |
| ⑥ **查询 + 写结论** | 三表 JOIN / GROUP BY / HAVING 回答三个问题，画图，写清机制与不足 | `query_results` / `figures` / `notes` |

材料配合：`task.md`（需求 + 口径）→ 读 `reference/`（一份**走完这六步**的示范）→
回 `scripts/run_sql.py` 填掉你自己的 TODO → 两个 case 都跑 → 补全下面的能力边界与实测档案 → 提交。

## 要做的决策（本实验的重点）

1. **表怎么划分**：为什么是"患者—就诊—检验"三层，而不是一张大表？分层的代价是什么（要 JOIN）？
2. **主键选谁**：为什么不用 `name` 当主键？（提示：重名、会改）
3. **外键要不要开**：SQLite 的 `PRAGMA foreign_keys` 默认是关的 —— 打开它之后，
   "补录一条引用不存在就诊的报告"会发生什么？这个行为对科室是好事还是麻烦？
4. **清洗顺序**：为什么必须"先校验、再去重"、"先 patients 再 labs"？顺序反过来会错在哪里？

  python3 scripts/run_sql.py "$c" "/tmp/$(basename "$c").json"
