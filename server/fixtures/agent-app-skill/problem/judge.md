# 评分细则（教师用）

**总分 100 = 需求 20 + 代码 40 + 演示 40。没有自动判分，不比对任何标准答案。**

## 需求（20）

| 分 | 看什么 |
|---|---|
| 17-20 | 这件事真的有人反复问；范围划得清（做哪块、不做哪块）；数据来源说清楚了 |
| 12-16 | 事情是真的，但范围含糊（"什么都能问"）或数据来源没说 |
| 6-11 | 需求是编的（为了做题而编），看不出谁会用它 |
| 0-5 | 没有需求，直接开始写代码 |

## 代码（40）

| 项 | 分 | 看什么 |
|---|---|---|
| 能跑起来 | 15 | 装到平台上是能对话的，不报错、不需要人肉改配置 |
| 解决问题 | 15 | 对它自己声明的那个需求，答案是**能核对**的（有数据/出处/规则支撑） |
| 说得清 | 10 | 三言两语讲明白：材料从哪来、怎么找、怎么答 |

## 演示（40）

| 项 | 分 | 看什么 |
|---|---|---|
| 现场跑通 | 15 | 学生自己操作，常见问题答得住 |
| 讲清取舍 | 15 | 为什么这么做、试过什么、放弃了什么、哪里没想到 |
| 边界意识 | 10 | 知道自己不能答什么（安全 / 诊断 / 用药），并且真的拒答 |

## 该扣的

- 答的东西无从核对（"建议多休息"这类）；
- 涉及安全 / 诊断 / 用药直接下结论；
- 讲不清自己的代码在干什么。

## 不该扣的

- 用规则不用模型、范围小、界面朴素 —— 都是设计选择；
- 需求不"高大上"（比如只是帮自己查课表）—— 只要真的有人用、能量化地核对，就是好需求。

> 教学提醒：这一章评的是"他能不能自己定义一个值得做的问题并做出来"。
> 演示多问「谁会用、什么时候会用、它答错了怎么办」。
