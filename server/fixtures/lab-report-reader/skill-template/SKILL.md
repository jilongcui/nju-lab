# 检验报告解读 Skill（你的方案）

> **本实验是应用任务，不是"按口径写代码"**：给你一个真实需求（社区医院要把报告解读流程固化成一个
> Skill），**代码怎么组织、图怎么画、文案怎么写由你自己决定**。清洗口径与判定口径是业务规则
> （必须照做），但"怎么实现"是你的自由 —— 达标看的是"口径一致 + 危急值抓得全 + 不确定的如实报
> + 不越界 + 说得清"。

## 实验材料（都在题目包 `problem/` 里，领取后工作区就有）

| 材料 | 作用 |
|---|---|
| `task.md` | **题干**：业务背景、六步流程、清洗口径、判定口径、交付格式 |
| `judge.md` | 判据：哪些是硬性口径、哪些是语义判断 |
| `reference/` | 一份**示范实现** —— 先读它，再写你自己的（它不是标准答案；函数划分与你的骨架一致） |
| `cases/case01`、`cases/case02` | 两批数据，自测用（每个 case 有 `expected.json` 可以对照） |

**实验流程（六步，与 `task.md` 一致 —— 每一步都要走完）**：

| 步 | 做什么 | 落在哪 |
|---|---|---|
| ① 看清需求 | 谁用、什么算解决、**哪些话不能说**（安全边界） | 报告的 `skill_card` |
| ② **读材料** | 报告单只有"项目/值/单位"，判定依据在**参考区间表**里 —— 先看清两份文件怎么对应 | 报告的 `items` |
| ③ **清洗归一** | 全角转半角 → 去空白 → 丢空值/非法值 → 同名项目只留首次（顺序不能反） | 报告的 `dropped` |
| ④ **逐项比对** | 判 `normal / high / low / unknown`，并判危急值 | 报告的 `items` / `unknown_items` |
| ⑤ **报警 + 画图** | 危急值逐条给出依据阈值；把偏离参考区间的程度画成一张图 | `critical_alerts` / `figures` |
| ⑥ **写结论** | 讲清结论与就医提示、讲清口径与局限 | 报告的 `summary` / `notes` |

材料配合：`task.md`（需求 + 口径）→ 读 `reference/`（一份**走完这六步**的示范）→
回 `scripts/read_report.py` 填掉你自己的 TODO → 两个 case 都跑 → 补全下面的能力边界与实测档案 → 提交。

## 要做的决策（本实验的重点）

1. **什么下沉给脚本、什么交给模型**：区间比对、危急值判断为什么必须由代码完成？
   如果让模型自己"看一眼"，最可能在哪一类值上出错？
2. **`description` 怎么写才算"触发路由"**：它要写清哪四件事？漏掉"不适用场景"会发生什么？
3. **不确定的项怎么办**：区间表里没有的项目，为什么必须判 `unknown` 而不是"猜一个正常"？
   在真实医疗场景里，"猜"和"说不确定"哪个代价更大？
4. **"拦截"落在哪**：本实验把正文里的 `hooks` 落成了 `critical_alerts` + `summary` 的就医提示 ——
   如果要继续加一道拦截（例如"任何结论都必须带上依据阈值"），你会加在哪一步？

## 自测

两个 case 都要跑，并自己与 `cases/<case>/expected.json` 对照（口径对不对，一眼就能看出来）：

```sh
for c in cases/*/; do
  python3 scripts/read_report.py "$c" "/tmp/$(basename "$c").json"
done
```

> 卡住了怎么办：先看 `reference/scripts/read_report.py` 里对应的那一段，再回来改自己的实现。
