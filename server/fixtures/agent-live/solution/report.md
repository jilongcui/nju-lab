## 3. agent 是怎么循环的

- 系统提示里钉死四件事：角色与语气、工具名册（JSON 原样贴进去）、动作格式（只允许一个 JSON 动作）、
  `KB-05` 的边界；另把 `limits.messages.refuse_lifetime` 的原话作为拒答话术参考。
- 动作格式：`{"action":"tool","tool":"overdue_assets","args":{"site":"A 区"}}` /
  `{"action":"finish","text":"…"}`。
- 步数上限取 `limits.max_steps_per_turn`（4）；用尽时把最后两条观察整理成答复，并记 `max_steps`。
- 模型给了不存在的工具：`run_tool()` 返回"未知工具：…（可用：…）"当作观察回填，让模型自己纠正。

## 4. 踩坑记录

1. `parse_action` 起初取"第一个 `{` 到最后一个 `}`"，模型连发两个动作时整段解析失败、把 JSON 当答案 —— 改成 `raw_decode` 只取第一个完整对象。
2. 台账 `site` 原本写成"A 区车间"，而用户说的是"A 区"，精确匹配全空、`overdue_assets(site=…)` 恒返回空 —— 数据改成 `site` + `location` 两列。
3. 拒答判定起初用"回答里出现不能"，把 T3 正常轮次误判成拒答，触发"拒答轮不得有引用" —— 改成"用户要寿命结论 + 回答明确拒绝"。

## 5. 结论

最容易出错的是**观察回填**：不回填或回填成"已查询"，模型下一步就在原地猜（表现为同一工具连调三次、参数越改越宽）。
记忆用条目表 + 状态，更正才真的生效；代价是抽取规则只认两种句式，这是最大局限。检索用字符 2-gram 加长度归一，
手册一多就会被长段落稀释。
