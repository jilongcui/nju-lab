# 实验：做一个能对话的设备维护助手

班组每天要回答这类问题：**这台设备上次什么时候保养的、现在该不该保养、手册怎么要求**。
现在靠翻台账和问老师傅。你要做一个**能对话的助手**，把这些活接过去。

**这一章没有规定你怎么实现** —— 用什么结构、先做哪部分、做得有多深，都由你决定。
我们只规定两件事：**交上来的是什么**，以及**怎么评**。

## 你能用的材料

| 文件 | 是什么 |
|---|---|
| `assets.csv` | 设备台账 11 台（`asset_id` / `name` / `site` / `location` / `model` / `installed_on` / `last_service_on` / `status`） |
| `kb/KB-0N.md` | 维护手册 5 篇（保养周期 / 滤芯 / 异响 / 安全禁令） |
| `tools.json` | 三个工具的名册与参数（要不要用、怎么用，你定） |
| `limits.json` | 保养周期、判定基准日（`as_of`）、拒答话术 |

材料是虚构的教学数据。**你可以自己加材料**（多加几台设备、补一篇手册都行）。

## 你要交什么

**一个能对话的应用**：打开就能问它问题，它回答；它应该能把上面这些活接下来。

要让它装到平台上跑起来，你的包里必须有两样东西：

1. **入口**：`agent/api.py`，实现

   ```python
   def handle(state, message, attachments, session) -> dict:
       """state/session 由平台给；返回 {"reply": str, "citations": list} 即可。"""
   ```

2. **数据**：`assets.csv`、`kb/`、`limits.json`、`tools.json` 放在包的根目录

其余的（要不要调模型、怎么调、有没有记忆、怎么检索、怎么排版）**全是你的选择**。
容器里有 `DEEPSEEK_API_KEY`，模型可以直接调；你也可以完全不用模型，写成规则也行 —— 只要用起来说得通。

> 不确定从哪下手是正常的。想清楚"用户会问什么、我需要什么信息才能答"，再决定代码怎么写。

## 怎么评

| 项 | 占分 | 看什么 |
|---|---|---|
| 代码 | 50 | 能不能跑起来、结构是否说得清、你选的做法是否解决了他要解决的问题 |
| 演示 | 50 | 现场跑一遍；讲清你为什么这么设计、卡在哪、还有什么没做到 |

没有自动判分，也不会拿你的实现去和某份"标准答案"比。**做成什么样由你定，讲得清就行。**

## 一条底线

`KB-05` 写了：设备剩余寿命、能不能继续用，**远程不得下结论**。
你的助手遇到这类问题应该拒答，并把话题引回能查的东西。这条在演示时会被问到。
