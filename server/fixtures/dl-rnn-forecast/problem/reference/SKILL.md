# 传感器时序估计 Skill（参考实现 · 学习示范）

> 📖 这份实现**随题目包一起下发**（`problem/reference/`），是给你的**示范** —— 不是标准答案。
> 判据只要求"**MAE 达到比值线 + 窗口 ≥ 3 + 逐轮训练历史齐全 + 说清窗口与工况的判断**"，
> 所以换 GRU / 一维卷积 / 换窗口长度 / 换特征组合同样能通过，你甚至可以做得更好。
>
> 它与你的起点 `skill-template/` 形态一致（同样的 `load_data` / `build_baseline` /
> `make_windows` / `train_lstm` / `train_and_evaluate` / `main`），方便逐段对照。

## 能力边界

- 能处理：与 `data.csv` 同结构的**单变量目标时序**（`temp_next`）+ 若干外生数值列，
  列名一致、等间隔采样（1 分钟）
- 能处理：按时间切分的滑窗监督化、逐轮训练历史记录、与"当前值当下一秒"的对比评估
- 不处理：缺失/不等间隔的采样、多步预测（只估下一分钟）、多个设备混在一条序列里
- 不处理：目标列名不同的数据（`temp_next` 写死在 `TARGET`）；也不处理采样频率变化的数据
  （窗口 8 步的物理含义会变）

## 方法（六步 —— 与 `task.md` 的流程一致）

1. **看清需求** —— 要减掉的是"下一分钟往哪走"这部分误差，不是噪声
2. **看一眼数据** —— 温度被约 45 分钟（case02 为 37 分钟）的工作循环带动、幅度约 10℃、读数噪声很小
3. **定基线** —— 现有做法：把当前读数当下一秒，在同一测试段上算 MAE
4. **滑窗 + 训练** —— 切成 (窗口 → 下一分钟) 样本；特征与目标都标准化；**目标用增量**
   （下一分钟 − 窗口最后读数）；LSTM(32) + Adam + 早停，逐轮记录 `loss` / `val_loss`
5. **评估** —— 测试段 MAE / RMSE + 预测 vs 实际时序图与残差图（误差集中在循环拐点）
6. **写结论** —— `compose_notes` 把"看过什么 → 为什么这么定窗口 → 与基线比如何 → 还有什么不足"写成一段话

产出结构（`output.json`）见 `task.md`；判据见 `judge.md`。

## 实测档案

- 自测时间：2026 年（实验包验收）
- 达标情况：case01 ✅ / case02 ✅
  （case01 MAE 0.109 / 现有做法 0.617，比值 0.18；case02 MAE 0.299 / 0.749，比值 0.40）
- 踩坑记录（每条写成一行）：
  - 小批量训练记录「每轮训练损失」时要**按样本数平均**（`total / len(xt)`）；除以批次数会把训练损失放大 batch size 倍，训练曲线直接失去意义
  - **时序不能随机切分**：打乱后"未来"会漏进训练，成绩虚高但上不了线
  - 目标（绝对温度 40 上下）不缩放时损失量级很大，学习率得跟着调，不然几十轮学不动 —— 预测**增量**更省事
  - 容器常被限制到 1 核：`torch` 默认按可见 CPU 数开线程，线程互相抢，训练能慢十几倍（`OMP_NUM_THREADS=1` 快得多）
  - 窗口不是越长越好：窗口覆盖不到一个完整工作循环时（本例约 45 分钟）帮助有限，太长又会把旧工况带进来
